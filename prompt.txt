# 0. ABSOLUTE ENGINEERING RULES
============================================================

These rules are mandatory.

RULE 1 — DO NOT IMPROVISE THE ARCHITECTURE.

Do not replace the chosen architecture, framework, database, AI abstraction, or publishing architecture merely because another technology appears easier.

If a change is technically necessary:
1. explain why,
2. identify the affected components,
3. propose the smallest possible change,
4. wait for explicit approval before changing architecture.

RULE 2 — BUILD IN PHASES.

Never attempt to build the entire application in one uncontrolled pass.

The project is divided into phases.

Only implement the CURRENT PHASE.

After the current phase passes its quality gate:
- document what was completed,
- document what remains,
- stop.

Do NOT automatically start the next phase.

RULE 3 — PRESERVE BACKWARD COMPATIBILITY.

Existing functionality must not be broken by a new phase.

Before modifying an existing component:
- inspect its current implementation,
- identify dependencies,
- preserve public interfaces unless a migration is required.

RULE 4 — NO FAKE FUNCTIONALITY.

Do not create buttons that pretend to work.

Do not create fake API responses and present them as real functionality.

If an external service is not configured:
- implement the adapter/interface,
- show a clear configuration state,
- provide safe mock/demo data only where explicitly marked as demo.

Example:

GOOD:
"Buffer is not configured. Connect Buffer API."

BAD:
"Post published successfully"
when no post was actually published.

RULE 5 — NO HARDCODED SECRETS.

Never put:
- API keys
- service-role keys
- OAuth secrets
- database passwords
- access tokens

inside source code.

Use environment variables.

Create/update:

.env.example

Never commit .env.local.

RULE 6 — USE OFFICIAL DOCUMENTATION.

When implementing external integrations:
- use official documentation,
- verify current API contracts,
- do not rely on outdated examples,
- do not invent endpoints,
- do not invent SDK methods.

If documentation is ambiguous, stop and report the ambiguity.

RULE 7 — DATABASE FIRST.

Business-critical state must be persisted in PostgreSQL/Supabase.

Do not use local component state as the permanent source of truth for:
- content
- campaigns
- business profile
- brand information
- scheduled posts
- AI usage
- social accounts
- analytics

RULE 8 — TYPE EVERYTHING.

Use TypeScript strict mode.

Avoid:
- any
- unsafe casts
- untyped API responses
- duplicated interfaces

Use shared schemas/types.

RULE 9 — VALIDATE INPUTS.

Use Zod or an equivalent schema validator for:
- API inputs
- AI structured outputs
- forms
- provider responses
- publishing payloads

RULE 10 — SERVER-SIDE SECRETS.

AI provider calls, Buffer calls, OAuth exchanges, and secret operations must happen server-side.

Never expose secret credentials to the browser.

RULE 11 — MOBILE FIRST.

Every screen must work on:
- mobile,
- tablet,
- desktop.

Desktop is NOT allowed to be the only design target.

RULE 12 — ACCESSIBILITY.

Use:
- semantic HTML,
- keyboard navigation,
- visible focus states,
- accessible labels,
- appropriate contrast,
- reduced motion considerations.

RULE 13 — PERFORMANCE.

Avoid unnecessary client components.

Prefer:
- Server Components,
- server-side data fetching,
- streaming where appropriate,
- lazy loading,
- optimized images,
- pagination.

RULE 14 — DO NOT OVERENGINEER.

Build only what is necessary for the current phase.

Do not introduce:
- microservices,
- Kubernetes,
- Redis,
- Kafka,
- complex event buses,
- unnecessary queues,
- unnecessary third-party libraries

unless a future phase explicitly requires them.

RULE 15 — DOCUMENT ARCHITECTURAL DECISIONS.

Create:

/docs/architecture/DECISIONS.md

Record important decisions using:

ADR-001
Title
Context
Decision
Reason
Alternatives
Consequences

RULE 16 — EVERY PHASE MUST HAVE A DEFINITION OF DONE.

A phase is NOT complete because the UI exists.

It is complete only when:
- implementation exists,
- types pass,
- lint passes,
- build passes,
- relevant tests pass,
- no obvious runtime errors exist,
- UI has been visually checked,
- documentation is updated.

RULE 17 — DO NOT DELETE FUNCTIONAL CODE WITHOUT JUSTIFICATION.

If code is obsolete:
- mark it,
- explain why,
- remove only after confirming no dependencies.

RULE 18 — KEEP THE AI LAYER PROVIDER-AGNOSTIC.

Never couple business logic directly to Gemini/Groq/Cloudflare.

Business code calls:

AI ROUTER

AI Router calls:

PROVIDER ADAPTER

Provider adapters call:

EXTERNAL AI PROVIDER
